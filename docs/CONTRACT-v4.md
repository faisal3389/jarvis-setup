# Jarvis v4 — one worker registry (`workers.json`) + a Tester worker

Read `docs/CONTRACT-v3.md` first (paths rule, ownership style, safety). Do not edit this file.
Never open/print/cat `.env.local`. Never commit or push. Do not stop or use port 4777 (the owner is using it).

## Goal
Adding a worker must need only TWO things:
1. `.claude/agents/<id>.md` (the subagent: frontmatter `name: <id>`, description, tools, model + worker protocol body)
2. one entry in `workers.json`

Everything else (board validation, Manager + Jarvis brain prompts, Manager tool allow list, reset folders,
Mission Control pills/colours/board/telemetry) reads `workers.json`. No other hard-coded worker lists remain
(except the page's offline fallback list, used only when `data/workers.js` cannot load).

## `workers.json` (project root, committed)
```json
{
  "version": 1,
  "workers": [
    {"id": "scout", "label": "SCOUT", "color": "#4fd1ff",
     "summary": "Numbers and analysis from the business data in sources/. Read-only.",
     "output": "outbox/analysis", "extraBash": []}
  ]
}
```
- `id`: lowercase `[a-z][a-z0-9-]{1,23}`; must equal the subagent file name and its frontmatter `name`.
- `label`: shown on the page (UPPERCASE, ≤ 12 chars). `color`: hex `#rrggbb`.
- `summary`: one sentence; shown to the Manager, the Jarvis brain, and as a page tooltip.
- `output`: the worker's output folder (relative); `bin/reset.sh` creates it (+ `.gitkeep`) and clears it.
- `extraBash`: extra Claude Code allow rules for Manager runs, e.g. `["Bash(npm test*)"]`. Keep `[]` unless
  truly needed — every rule widens what ALL workers may run.
- Order in the file = order on the page.
- Workers: scout (cyan), operator (violet), developer (teal), researcher (pink) — copy their exact hex values
  from the page's existing CSS variables — and the new **tester** (lime/green that fits the palette).

## Who reads it
- `bin/board.py`: `WORKERS` = ids from `workers.json` (clear error if the file is missing/invalid).
- `server.mjs`:
  - `GET /data/workers.js` (virtual, generated on every request from `workers.json`):
    `window.JARVIS = window.JARVIS || {};\nwindow.JARVIS.workers = [ …the workers array… ];`
    (static `data/` serving must not shadow it). `GET /api/workers` returns the same JSON.
  - Manager runs: `--allowedTools` = existing list + every worker's `extraBash` (deduplicated); event prompt gets a
    `WORKERS:` block (`- <id>: <summary> (output: <folder>)`) right after the EVENT line.
  - Jarvis brain prompt: add a compact `WORKERS:` line (ids + summaries) to the context block.
  - On startup: warn (console) for any worker without `.claude/agents/<id>.md` or with a mismatched `name:`.
- `MANAGER.md` / `JARVIS.md`: replace hard-coded worker lists with "the WORKERS block in your prompt";
  keep worker-specific mode notes (scout daily report, operator inbox sweep, developer workspace rules).
- `bin/reset.sh`: output folders from `workers.json` (plus the existing fixed folders).
- Page (`mission-control/index.html`): loads `../data/workers.js` with the other data files (fixtures:
  `fixtures/workers.js`); header pills, board worker chips, board footer status rows, telemetry colours and
  legends are all generated from `window.JARVIS.workers` (fallback = built-in list of the 5 workers).

## The Tester worker
`.claude/agents/tester.md` — checks other workers' work, never fixes it.
- Developer output: reads `workspace/task-<id>/`, runs its checks with `python3`, tries edge cases.
- Drafts/reports with numbers: verifies every number and claim against `sources/` and the earlier task's files.
- Writes `outbox/tests/task-<id>.md`: verdict PASS / FAIL / PARTIAL, a table of checks (check, expected, actual,
  result), and exact problems for the worker who must fix them.
- Tools: `Read, Glob, Grep, Write, Bash` (Bash = `python3` only; same no-redirect / no-chaining rules as the
  other workers). model: sonnet. `extraBash: []`.
- Manager guidance (MANAGER.md): when a task produces code, or a draft whose numbers matter, add a tester task
  that `dependsOn` it; on FAIL give the producing worker one redo with the tester's problems, then re-test once.
  Raise the per-request task cap from 4 to 5 to make room.
